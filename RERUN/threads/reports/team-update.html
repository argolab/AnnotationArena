Three architecture decisions before the final runs

Three threads ran in parallel, each asking whether a piece of the model earns its place. All three are now settled. Headline: the model simplifies to a standard Transformer block, the learned value codec works wherever there is enough data but is not yet safe on small data, and the context window should be fixed at 500 items.

Thread 3

Does the block need its extra linear and its duplicated residual?

The block we have been shipping is not a standard Transformer block. It carries two extra pieces. First, a trailing d×d linear projection applied to the block’s output. Second, an outer residual add that re-injects the input around that projection, so the block computes h′ = h + M(c) where c = h + attn + ff — the input is added twice, once inside c and once outside. A standard block is just h′ = c.

We ran four variants at K=300 and K=2000, three model seeds × two independent data draws, six paired runs per cell.

Takeaway 1 — at K=2000 the standard block is not merely equal, it is better

Removing both pieces buys 0.021 nats, and all three readings agree to within 0.003, so this is not an artefact of how the checkpoint was chosen. Both variants that drop the outer add beat the shipped block at this size; the one that also drops the linear wins by the most. Freezing the linear rather than removing it recovers almost nothing, which tells us the projection is not doing something that merely needs to exist — when it is on the residual path at all, it is in the way.

Takeaway 2 — the old “remove the outer residual” regression was the linear, not the residual

Earlier we saw that removing the outer add alone (proj_keep_rot) hurt at small data, and that was the reason we had not simplified. It reproduces here: +0.150 at K=300 under the real protocol. But removing the linear as well cuts that to +0.052 — and at the best epoch, to +0.007. The mechanism is visible in the trained weights: the projection has no identity component (its alignment with the identity is −0.003, and its effective rank is 57.5 of 80). So when the outer add is removed, every layer’s identity path is pushed through a dense, near-random rotation, eight times over the stack. The skip connection stops being a skip. Remove the rotation too and the path is clean again.

The two pieces were never independent. Taken one at a time each looks load-bearing; taken together they cancel, and what is left is the standard block.

Correction worth carrying — the linear is not free to delete

It was suggested that since the feed-forward ends in a linear with no activation after it, the block’s trailing projection composes with it and can be deleted without changing the function. That is true only when the inner residual is off. In the shipped block the projection is applied to h + attn + ff, not to the feed-forward output alone, so there is no adjacent linear to absorb it. Checked numerically against the real forward pass: with the inner residual off the fold is exact (relative error 1.8×10−7); with it on, the same substitution moves the output by a relative 162. Deleting the linear is a real ablation — which is why it had to be run.

Caveat — at K=300 the simplified block is harder to stop

At its best epoch proj_drop_rot is at parity at K=300 (+0.007). Under the actual protocol it costs +0.052. The difference between those two numbers is stopping regret, and it is much larger for the variants without the outer add than for the shipped block, whose regret at this size we measured separately at about +0.018. With a dev block of only ~110 targets at K=300, these variants are harder to early-stop reliably. If the paper reports small-K rows, this is the honest qualifier: equal architecture, worse stoppability.

Thread 2

Replacing the hand-built value slots with a learned codec

Today a rating enters the model through a hand-built layout: one slot marking “hidden”, then one slot per rating level, filled in by hand and read back at the end. It works and it only works for ratings. The alternative is a per-type encoder into the model’s space and an untied decoder back out to a distribution — nothing type-specific written by hand.

We first proved the new design contains the old one: initialise the encoder to write into exactly the hand-built slots, freeze it, and the two are the same function, bit for bit, including through the batched training path. So any difference had to come from how it trains.

The regression was on the input side, not the output side

The working theory had been that the codec regressed because the decoder could not produce a sharply peaked distribution. That turned out not to be the cause. The cause is at layer zero: the hand-built layout writes the observed value into the stream with magnitude 20 — a deliberate constant that has been in the code from the start — while a freshly initialised encoder, using the default convention for a new layer, writes about 0.02 per entry. The observation the model is supposed to condition on arrived essentially inaudible, and training spent its budget turning the volume up instead of learning to use the value.

Three pieces of evidence pin this down. Arms that start from the hand-built layout land at parity whether frozen or free to move, so the architecture and training path are sound. Only arms that start random fail. And scaling the encoder — one line, still fully random, just no longer whispering — closes the entire gap at K=2000.

The scale is a threshold, not a calibration — so the constant is gone

The first fix that worked set the encoder’s std to logit_high / sqrt(model_dim), which puts the value in the stream at norm 20 — matching the hand-built slot exactly. That works, but it leaves the hand-built constant in the loop, which defeats half the point of learning the code rather than writing it.

So we tested whether the exact magnitude matters, with a plain N(0,1) encoder that contains no constant at all. Six paired runs at K=2000, two draws × three seeds:

N(0,1) is at parity — at or below the reference in five of six cells, and the −0.009 is under the 0.015 decision threshold, so it should be read as a match rather than an improvement. What matters is where the failure sits: norm 8.9 clears the bar at less than half the hand-built magnitude, norm 0.18 does not, and the crossing is somewhere between.

The encoder has to be loud enough, not calibrated to any particular number. logit_high can leave the codec path entirely — which was the point of learning the code in the first place.

codec_init now defaults to unit. Two limits worth stating: this was measured at K=2000 only, so it says nothing about the small-data failures below; and logit_high still governs the hand-built dual stream, which remains the default. The constant is out of the codec path, not out of the codebase.

Did we ultimately match the old system? At K=2000, yes

+0.002 nats, with zero failures in six runs. One line of initialisation, and the learned codec is indistinguishable from the hand-built stream. At K=300 the mean is +0.032 but the mean is the wrong summary, which is the next point.

The temperature idea did not work, and its failure is informative

The proposal was to give the decoder one extra output, treat it as a softmax temperature, and let it learn to emit 0.05 — reproducing the 20× sharpening the constant provides for free. It is implemented correctly (the head is there, the decoder gains a row) but the model never learns to use it: after 400 epochs the temperature sits at 0.976, no sharpening at all. Worse, its presence costs 0.19–0.27 nats over the same architecture without it, because dividing every logit by a still-noisy quantity makes the early objective harder.

This is the expected outcome once the diagnosis is corrected: the temperature head was designed to fix an output-side problem, and the problem is on the input side. It has now been purged from the code rather than left switched off, and codec_init defaults to the volume-matched draw. Committed on side/value-codec as 4d6841f; the equivalence check still passes at max abs diff 0.0.

Would training longer help? Probably not — but we did not test it directly

Stating this plainly since it is a natural question. We did not run a longer-budget arm. The indirect evidence argues against a budget explanation: the arm that starts from the hand-built layout reaches parity within the same 400 epochs, so there is no slow-convergence penalty intrinsic to the architecture; and the small-data failures below are seed-locked basins rather than incomplete descent. If we want this closed properly it is one cheap arm.

What is actually left — instability at small data, and initialisation cannot fix it

We tested the obvious suspect: a random encoder can be loud and still have its directions bunched together, so we drew it orthogonally — loud and well-conditioned. It changes nothing. Twelve paired runs per arm at K=300:

Status: the codec is correct when selected, but value_codec still defaults to the hand-built dual stream. Switching the model over stays blocked on the small-K failure rate.

Thread 1

How wide should the context window be?

Training splits the item graph into chunks of at most max_item items. We had been training at 300 and evaluating at 500. The question was whether a wider window helps at the large training sizes where the gap against the reference method is widest.

It does, by a small and completely reliable margin

Six of six cells agree in sign and the mean is five standard errors from zero. The paired standard deviation is 0.0071 — five times tighter than the 0.035 we see between different architectures — because this varies one knob rather than training a different model. The figure is 0.016 nats, not 0.02. Small in absolute terms, but the residual gap against the reference method is about 0.10 nats, so this single knob is roughly a sixth of the thing we are trying to close.

One incidental finding that matters for any future comparison: each arm prefers an evaluation chunk at or above the one it trained with. Training and evaluation window are not independent knobs, so every arm has to be read at its own best rather than at a shared chunk.

500 costs 5% more wall clock than 300 and leaves 24 GB of headroom. 600 fits but with almost none, and 900 does not fit at all. Decision: train and evaluate at 500.

Does a dynamic window buy more? No — and it costs 4.2×

The idea: draw the chunk size fresh each epoch from a range (we used 100–500, one draw per epoch so nothing zigzags inside a forward pass), and hope the model learns to handle windows wider than any it trained on — letting evaluation run at 700, 900, 1200 where memory during training is not the constraint.

Read each arm at its own best and pair the runs: dynamic is +0.0021 ±0.0016 against fixed-500 — indistinguishable, with the sign the wrong way. It does not win at any evaluation width, including 900 and 1200 where neither arm trained. The extrapolation rationale is simply absent.

Against that it costs 4.2× in training time: 10.3–10.8 s/epoch versus 2.45 for both fixed arms at K=4000, because re-sampling the window each epoch rebuilds the item graph and that dominates the step. Decision: do not adopt dynamic chunking.

The reason the idea had nothing to buy: fixed-500 already extrapolates. Its best evaluation width is 700–900, not the 500 it trained at, and it is still better at 1200 than at 300. Training at a fixed wide window teaches the generalisation a dynamic schedule was meant to teach.

A useful cross-check falls out of this sweep: fixed-300 against fixed-500 comes out at +0.0155 ±0.0046 here, against the −0.016 ±0.003 measured earlier on separate scoring machinery. Two independent readings of the same knob agreeing to a thousandth of a nat.

Also settled along the way

Early stopping does land in the basin

A question raised in review: the stopping epoch must be chosen on a validation set, not on test, and the charitable assumption is that validation finds a point close to the test minimum. We measured it rather than assuming it, on paired runs sharing a data draw and model seed. Across twelve training sizes the dev-chosen epoch costs 0.016 nats against the best epoch the test curve could have given, worst case 0.029 — inside the noise of a single architecture comparison.

The mechanism is worth stating correctly, because it is a stronger argument than accuracy: the selection is often badly off (at K=700 it picks epoch 362 where the test minimum is at 200) and it barely matters, because the basin is flat across 100–250 epochs. The selector does not have to be right, only to land in the basin. One exception: at K=100 the training partition has no items to carve a validation block from, so there is no signal to select on at all and the protocol falls back to an axis median.

Observed-token loss sits at 10−5 and below at every size and every epoch in every arm, so all movement in these curves is the missing-rating term.

Where to look RERUN/threads/early-stopping/ — e1_stopping_regret.py, which imports the shipped selector rather than reimplementing it.

How everything above was measured. All comparisons are paired: each arm trains on the same data draws and model seeds as its reference and is compared run by run, because the choice of draw alone moves this metric by 0.085 nats — several times the effects in question. Where a column says “dev-selected”, the stopping epoch came from a block of held-out training items and nothing was chosen on test. Where it says “best epoch”, the checkpoint was chosen on test and the number is a ceiling, shown only to separate an architecture effect from a stopping effect.
